Giới thiệu framework

Nhu cầu, phạm vi, cấu trúc repo, kiến trúc, điểm mạnh (kèm bằng chứng) và giới hạn hiện tại.

Đúng với commit 175df65 (nhánh 012-analytics-audit, tài liệu làm trên docs-html-guides).

1. Framework này giải quyết nhu cầu gì #

Một backend dùng chung cho nhiều game mobile. Mỗi game Unity cần cùng một nhóm việc: đăng nhập, lưu tiến trình và tài nguyên, mua IAP, công cụ GM, log, kiểm soát bảo trì. Framework làm sẵn các phần chung đó; mỗi game chỉ viết phần nghiệp vụ riêng (command, rule, aggregate) dưới dạng module, và không sửa core.

Server là nguồn sự thật (server-authoritative). Client gửi hành động (ví dụ "kết thúc trận, thắng"), không gửi kết quả ("tôi có 500 gold"). Server kiểm tra, tính kết quả, lưu, rồi trả về phần dữ liệu đã đổi. Client không bao giờ tự quyết số dư. (Yêu cầu PLY-01, Requirements/Game_Server_System_Requirements_v1.2.md mục 8.1.)

Kiểu giao tiếp: HTTP request–response. Unity dùng HTTPS + Protobuf; GM tool web dùng HTTPS + JSON. Không có realtime tick, UDP hay đồng bộ di chuyển (ngoài phạm vi, yêu cầu mục 2.1).

Ba mục tiêu chính của tài liệu yêu cầu (mục 1), mỗi mục được đo bằng tiêu chí nghiệm thu:

#Mục tiêuĐo bằng (ID yêu cầu)
1I/O bất đồng bộ, chịu được tải dồn: không sync-over-async, giới hạn hàng đợi có sốPERF-01..10, ACC-16, ACC-52
2Kiến trúc module: thêm module/command/policy mà không sửa Core; game tự định nghĩa dữ liệu playerARC-01..10, EXT-01..05, ACC-13
3Xác thực, phân quyền, audit GM thống nhất cho module cũ và mớiSEC-02, SEC-07, SEC-08, SEC-14, ACC-09..12

Công nghệ nền: C# / .NET 10 (SDK 10.0.403 ghim trong global.json), ASP.NET Core + Kestrel, Minimal API, Couchbase ≥ 7.6 (distributed transactions bắt buộc), Google.Protobuf (cùng một version ở server và Unity).

4. Kiến trúc #

4.1 Sơ đồ khối (Sơ đồ A) #

Mô tả dạng chữ của sơ đồ A (khối và mũi tên)

Đặc tả để vẽ. Bố cục từ trái sang phải, ba cột.

Cột trái — Client

  • Hộp Unity game chứa hộp con com.gameserver.client (GameServerClient).
  • Hộp GM tool (web).

Cột giữa — một hộp lớn "Host process (ASP.NET Core + Kestrel)", bên trong xếp từ trên xuống:

  1. Dải ngang Middleware pipeline: các ô nối tiếp ForwardedHeaders → ExceptionMiddleware → CorrelationMiddleware → Routing → GateMiddleware → ProfileEnforcementMiddleware (auth) → RequestTimeouts → RateLimiter.
  2. Dải ngang Endpoints: ô Player API (Protobuf) /api/v1/..., ô GM API (JSON) /gm/v1/..., ô Public /v1/time, login, /health/*.
  3. Hộp Platform: ô CommandRunner, ô ModuleRegistry, ô Outbox relay + sweeper, ô Lease jobs, ô Analytics pipeline.
  4. Dải ngang Modules (mỗi module một ô): Identity, Economy, IAP, GM, SampleGame, Sample.Counter, ô nét đứt Module của game.
  5. Hộp Core (contract) nằm dưới cùng, mỏng, có nhãn "Modules chỉ phụ thuộc Core".

Cột phải — Hạ tầng

  • Trụ Couchbase (nhãn: "bucket theo môi trường, scope g_{gameId}, collection pa_*, receipts, …").
  • Trụ nét đứt File store (chỉ flavor Local).
  • Hộp Files: logs/*.json, analytics/*.jsonl.
  • Hộp OTLP collector (tuỳ chọn).
  • Hộp Apple / Google (verify IAP, identity).

Mũi tên

  • Unity game → dải Middleware pipeline: nhãn "HTTPS POST, Protobuf, X-Request-Id + Bearer".
  • GM tool → dải Middleware pipeline: nhãn "HTTPS, JSON, cookie + CSRF".
  • Endpoints (Player API / GM API) → CommandRunner: nhãn "command".
  • CommandRunner → Modules: nhãn "gọi handler".
  • CommandRunner → Couchbase: nhãn "1 transaction / command".
  • Outbox relay + sweeper → Couchbase: nhãn "projection".
  • Analytics pipeline → Files: nhãn "JSONL".
  • IAP module (thực ra endpoint IAP) → Apple / Google: nhãn "trước transaction".
  • Host → OTLP collector: nét đứt, nhãn "traces, metrics".

4.4 Mô hình "một command = một transaction" #

Đây là ý quan trọng nhất của framework. Mọi thao tác làm đổi dữ liệu player là một command:

  • Aggregate: dữ liệu player chia thành các khối JSON (aggregate), mỗi khối một document pa_{aggregateId} với key = playerId, có rev và schemaVersion. Ví dụ profile, wallet, inventory, counter. Tối đa 16 aggregate một game.
  • CommandDescriptor (src/GameServer.Core/Commands/CommandDescriptor.cs) khai báo trước: tên operation (<module>.<command>), Touches (aggregate được ghi, 1..4), Reads (chỉ đọc), số claim marker tối đa (0..2), security profile, permission GM.
  • CommandRunner (src/GameServer.Platform/Commands/CommandRunner.cs) mở một transaction Couchbase, đọc Touches ∪ Reads + receipt, gọi handler, rồi ghi các aggregate đã đổi (rev + 1), claim marker và receipt trong cùng transaction, commit. Handler không gọi database.
  • Receipt + replay (idempotency): client sinh X-Request-Id (UUID) cho mỗi command. receiptId = SHA-256(actorId | playerId | operation | requestId). Gửi lại cùng requestId và cùng body trong 24 h → server trả đúng kết quả cũ (replayed = true), không chạy lại. Cùng requestId nhưng body khác → 409 IDEMPOTENCY_PAYLOAD_MISMATCH.
  • Từ chối nghiệp vụ (CommandOutcome.Reject) → rollback, không ghi gì, không receipt; client nhận HTTP 200 với mã nghiệp vụ.
  • Outbox: hiệu ứng phụ (log, ledger, audit GM, analytics) là entry ctx.AddOutbox(kind, payload) nằm trong receipt, nên commit cùng lúc với dữ liệu. Sau commit, relay inline giao cho consumer; nếu lỗi, OutboxSweeper (mỗi 30 s) giao lại; quá 10 lần → dead letter. Consumer mặc định chiếu entry vào một collection (OutboxProjection).
  • Section / rev: response trả các aggregate client-visible đã đổi (SectionUpdate có base_rev, new_rev, payload Protobuf). SDK Unity giữ bản sao theo rev.
  • Nâng schema lười: tăng schemaVersion của aggregate thì khai một IAggregateUpgrader cho mỗi bước; document cũ được nâng khi đọc và ghi lại ở lần commit kế tiếp.

Chi tiết đường đi của một command và cách viết command mới: trang 5b (02-them-command.html).

4.5 Security profile và xác thực #

Mọi endpoint phải có đúng một security profile, gắn bằng helper trong src/GameServer.Platform.Web/Routing/ApiModules.cs:

ProfileHelperDùng choXác thực
PlayerAsPlayerEndpoint() (tự gắn bởi MapPlayerCommand)API game, ProtobufAuthorization: Bearer <token> → PlayerBearerAuthenticationHandler (session, profile: đã xoá → bị khoá → bị thay phiên)
GmAsGmEndpoint(permission) (tự gắn bởi MapGmCommand)GM API, JSONcookie GM + permission + CSRF cho thao tác ghi
PublicAsPublicEndpoint(...), AsPublicPlayerEndpoint()/v1/time, login, healthkhông; route phải nằm trong allowlist (GameServer:PublicEndpointAllowlist hoặc ModuleDescriptor.PublicEndpoints)

  • Deny-by-default: ProfileEnforcementMiddleware trả 403 cho endpoint không có profile, kể cả khi bộ kiểm tra lúc khởi động bị tắt.
  • Kiểm tra lúc khởi động (EndpointSecurityValidator): route thiếu /v{n}/, route trùng, Public chưa vào allowlist, Dev ở Production, GM mutation Public thiếu CSRF → host không khởi động.
  • Session một thiết bị: login mới tăng SessionEpoch của profile; token cũ nhận SESSION_REPLACED.
  • GM (slice 007): SSO OIDC, cookie, CSRF, CORS allowlist, Data Protection key ring lưu trong store, audit mọi thao tác ghi (mỗi GM command ghi đúng một entry gm_audit, runner kiểm).

4.6 Gate, ban và giới hạn tải #

  • Gate (GateMiddleware, slice 008): document gate chứa cờ bảo trì và version client tối thiểu theo platform. Chạy trước xác thực trên Player API và login; trả 503 MAINTENANCE hoặc 426 UPDATE_REQUIRED. Cache ≤ 10 s mỗi instance (GameServer:Gate:CacheSeconds). GM, health, Dev vẫn hoạt động.
  • Ban: ban login làm xác thực thất bại (ACCOUNT_SUSPENDED); ban theo nhóm command do BanCommandGuard (một ICommandGuard) chặn lần chạy mới trong CommandRunner, retry của command đã commit vẫn được replay.
  • Giới hạn (GameServer:Limits:*, GameServer:Commands:*): body Player ≤ 64 KiB, timeout Player 10 s, concurrency command toàn instance 200 + hàng đợi, mỗi player chạy tuần tự 1 command (hàng đợi 2, quá thì RATE_LIMITED).

4.9 Việc chạy nền #

  • Outbox sweeper (OutboxSweeper): giao lại outbox chưa giao, mỗi 30 s, an toàn khi nhiều instance (consumer idempotent).
  • Lease job (slice 010, LeaseJobRunner, contract ILeaseJob trong Core): job khai trong ModuleDescriptor.Jobs, mỗi lúc chỉ một instance giữ lease (document leases::{job}, fencing token).
  • Xoá tài khoản (slice 010): player gửi identity.request_deletion; job identity.account-purge xoá/ẩn danh dữ liệu theo DeletionTreatment mà mỗi CollectionSpec bắt buộc khai (NoPlayerData / Anonymize / Remove / ModuleStep).

4.10 Quan sát và audit #

  • Log: file JSON theo instance (rolling, hàng đợi có giới hạn, che secret) — src/GameServer.Platform.Observability.
  • OpenTelemetry: mỗi command là một span command {operation}; metric command, transaction, outbox. Gửi tới collector khi đặt Observability:Otlp:Endpoint.
  • Health: /health/live (không kiểm dependency), /health/ready (kiểm store, analytics…).
  • Audit bền: receipt (mọi command), ledger (Economy), gm_audit (mọi thao tác GM).
  • Analytics (slice 012): file JSONL {gameId}-{instanceId}-{event}-{yyyyMMdd}.jsonl cho login và payment. Payment ghi ít nhất một lần (nằm trong outbox của transaction cấp quà); login best effort. Module dùng ctx.AddAnalyticsEvent(...) (src/GameServer.Core/Analytics/AnalyticsEvents.cs). Hướng dẫn cho data team: docs/guides/analytics.md.

4.11 Unity client SDK #

Gói sdk/unity/com.gameserver.client (version 0.6.0), lớp chính GameServerClient (Runtime/Core/GameServerClient.cs):

  • Gắn header X-Request-Id, X-Client-Version, X-Platform, X-Build-Id, Authorization: Bearer cho mọi request.
  • SendCommandAsync(route, request, resultParser): serialize body một lần, retry gửi lại đúng bytes với cùng requestId → server replay, một hiệu ứng duy nhất.
  • Sections (SectionStore): bản sao aggregate theo rev; tự refresh khi lệch.
  • Sự kiện SessionReplaced, AccountBlocked, Maintenance, UpdateRequired, ConfigVersionChanged.
  • ServerNow: giờ server theo đồng hồ monotonic.

Client mẫu Unity 6: samples/SampleGame/KestrelDemo (scene SampleGameClient). Contract: docs/pcr/unity-sdk.md.

4.12 GM API #

GM API là JSON dưới /gm/v1/..., dùng chung pipeline command (receipt, idempotency, audit). Trang tĩnh tối thiểu /gm/v1/ui; GM frontend đầy đủ do dev khác làm dựa trên docs/api/gm-openapi.json (test tests/GameServer.Gm.Tests/OpenApiTests.cs bắt bản commit phải khớp host đang chạy).
