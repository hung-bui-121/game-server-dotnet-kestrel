# Feature Specification: Wire contract — one route catalog with endpoint check, consumer Unity codegen, section ↔ message contract and wire-mapper conformance (slice 014)

**Feature Branch**: `014-wire-contract`

**Created**: 2026-11-03

**Status**: Draft

**Input**: Owner-approved improvement round (2026-11-03) from the first consumer game `E:\ProjGits\zh-pvp-server` (submodule
`framework/` pinned to tag `v0.6.0`; Unity client `E:\ProjGits\research-and-development-games`), friction log
`docs/framework-feedback/FRICTION_LOG.md` of that repo. Four sequential slices, one tag `v0.7.0` at the end of the round;
013 (group A) is merged into `main`. This slice is group B:

- **FG-026**: HTTP routes have no shared catalog, so server and client copy route strings by hand. The owner chose
  **direction B at framework level** on 2026-11-03:
  1. one public server-side route catalog: framework routes are public, and games declare theirs through the same
     mechanism;
  2. codegen, extending the FG-021 path, generates route constants for Unity, and the SDK uses the generated file instead
     of hand-copied strings;
  3. a check enumerates every mapped endpoint and compares it with the catalog. A missing declaration or a mismatch fails.

  Rejected: A (one constant class per repo) and C (custom route option in `.proto`).
- **FG-028**: The snapshot contract does not record which proto message each section id carries, so the client picks a
  parser by hand.
- **FG-021**: There is no consumer path to generate Unity C# from a game's own `.proto`.
- **FG-027**: One aggregate is described by hand three times (C# state → proto → wire mapper), and nothing checks that the
  three agree.

  - Framework route constants are scattered and partly `internal` (`CoreEndpoints`). Some sample routes are inline string

  - Nothing compares the mapped endpoints with a declaration.

  - A state member added without a proto field or mapper line silently reaches the client as a protobuf default.
  - A game cannot generate Unity C# for its own `.proto` without editing a framework csproj or keeping its own generator
    project with line-ending and path workarounds.

  - Slice 015: config validation and distribution (FG-018, FG-023, FG-024, FG-019).
  - Slice 016: login/command robustness (FG-013, FG-015, FG-029, FG-016, FG-022).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Every server endpoint is declared once and checked against what is mapped (Priority: P1) — FG-026 (1), (3)

A framework or game developer declares each HTTP route once, with its HTTP method, security profile and owning module, in
one public catalog. The host refuses to start when an endpoint is mapped that the catalog does not declare, or when a
declared route is mapped differently from its declaration. Mapping code and any server-side code that needs a route
(request log, tests, consumer middleware) read the declaration instead of repeating the string.

**Why this priority**: This is the root of FG-026. Today a route typed differently in two places is found only by a 404 at
run time, and every game command added from P2 onwards adds another pair of copies. The catalog is also the input that the
codegen of stories 2 and 3 needs.

**Independent Test**:
- Start the sample host composition in each flavor, with and without the player and GM APIs mapped. Check that startup
  succeeds and that the public catalog lists every mapped endpoint.
- Start variants that each add one fault, and check that each fails startup with one report line naming the route and
  the fault. The faults are:
  - an undeclared player endpoint;
  - an undeclared GM endpoint;
  - an endpoint whose method differs from its declaration;
  - an endpoint whose profile differs from its declaration;
  - a command route whose operation differs from its declaration;
  - a declared route of a mapped module that is not mapped;
  - two declarations with the same name;
  - an undeclared endpoint mapped after `UseGameServer`.
- From a consumer-shaped test project, read the framework's route declarations (for example the config route) through
  public API only.

**Acceptance Scenarios**:

1. **Given** the framework's own modules and platform endpoints (time, snapshot, receipt lookup, config, health probes,
   identity, IAP, economy GM, cheat, GM auth/SSO/staff/players/ops/gate/version, GM OpenAPI document), **When** a
   consumer reads the route catalog, **Then** every route the framework can map is listed with:
   - a stable name;
   - the HTTP method(s);
   - the route template, including its parameters;
   - the security profile;
   - the owning module;
   - the command operation, when the route runs a command;
   - the surface it belongs to (player API, GM API, host endpoints);
   - any hosting condition under which it is mapped.

   Each entry is reachable from consumer code through public API (FG-026 (1), (4)).
2. **Given** a game module, **When** it declares its routes through the same mechanism the framework uses (alongside its
   module and command declarations), **Then** its routes appear in the catalog of any host that registers the module, and
   its mapping code can take the route from the declaration, so the route string is written once in the server code.
3. **Given** a host that maps an endpoint that no registered module or host declaration lists, whether it is mapped by a
   module or by the host's own `Program`, **When** the host starts, **Then** startup fails before serving traffic. The
   aggregated report has one line naming the method, the route and the fix (declare it).
4. **Given** a declared route, **When** the mapped endpoint differs from the declaration in route template, HTTP method,
   security profile or command operation, **Then** startup fails with one line naming the declaration, the mapped
   endpoint and the field that differs.
5. **Given** a module whose surface is mapped in this host (player API, GM API or host endpoints, and the module is not
   service-only), **When** one of its declared routes for that surface is not mapped and its hosting condition holds,
   **Then** startup fails, naming the module and the route. Routes of surfaces the host does not map
   (`Hosting:MapPlayerApi = false`, `Hosting:MapGmApi = false`, service-only modules), and conditional routes whose
   condition does not hold (GM OpenAPI outside Development/Test), are not reported.
6. **Given** an endpoint mapped after `UseGameServer` returned, **When** the host is about to serve its first request,
   **Then** the same endpoint validations apply to it as to endpoints mapped inside `UseGameServer`: the catalog check,
   security profile, versioned route, duplicates, Public allowlist, Dev rule and command route ↔ command. Any violation
   stops the host with the aggregated report and exit code 1.
7. **Given** two declarations with the same name, or with the same method and route template, **When** the host starts,
   **Then** startup fails, naming both owners.

### User Story 2 - A game generates its Unity C# from its own repository (Priority: P2) — FG-021

A game developer, with the framework as a submodule, runs one framework-provided generation step from the game repository.
The developer passes the game's `.proto` files, the output folder in the Unity client, the C# namespace for generated route
and section code, and the line-ending style. The step writes the message C# for those protos (importing, never
regenerating, the framework protos shipped in the Unity package), using the protoc version that matches the
`Google.Protobuf.dll` of the Unity package. Running it again without changes leaves no diff. No framework file is edited
and no private generator project is needed.

**Why this priority**: Every game with its own wire contract needs this before it can call any game command from Unity.
The first consumer spent 15 minutes, keeps a 70-line generator project with two workarounds (path separators, CRLF), and
`docs/html/02-them-command.html` §4.10 tells consumers to edit a framework csproj, which they are not allowed to do.

**Independent Test**:
- From `tests/ConsumerFixture` (or a second fixture), run the generation step with a game proto that imports
  `gameserver/core/v1/core.proto`, an output folder outside the framework, a namespace, and once each with LF and CRLF.
- Check that the output compiles with C# 9 / `netstandard2.1` against the Unity package sources and its
  `Google.Protobuf` version, outside Unity.
- Check that no framework proto type is generated into the output.
- Check that a second run gives byte-identical files and unchanged timestamps.
- Check that running from a checkout path with mixed separators gives identical bytes.
- Check that cleaning the project does not delete the generated files.
- Check that a wrong output folder or a missing proto fails with a message naming it.

**Acceptance Scenarios**:

1. **Given** a game repo with the framework submodule, **When** the developer runs the framework's consumer generation
   step with a list of proto files, import folders of their own (optional), an output folder and a namespace, **Then**
   C# is generated for exactly those protos into the output folder. The framework's proto import roots
   (`proto/`, the identity, economy and IAP proto folders) are available to `import` without being listed, and no file of
   the framework is modified.
2. **Given** a game proto that imports a framework proto, **When** C# is generated, **Then** the imported framework
   messages are referenced from the Unity package's generated types and never generated again into the game output. Two
   definitions of one message type in a Unity project are a compile error.
3. **Given** the same inputs, **When** the step runs twice, on different machines or from different checkout paths,
   **Then** every output file is byte-identical. Output is written in the selected line-ending style (LF or CRLF; the
   first consumer's client needs CRLF) and as UTF-8 without BOM. A file whose content did not change is not rewritten.
   The output contains no timestamp, absolute path, user or machine name.
4. **Given** the framework's pinned `Grpc.Tools`/protoc and `Google.Protobuf` versions, **When** a consumer generates C#,
   **Then** the protoc version used is the framework-pinned one, and the generated code targets the `Google.Protobuf`
   version shipped in the Unity package. If the consumer's build would resolve a different `Grpc.Tools` or
   `Google.Protobuf` version, the step fails, naming both versions.
5. **Given** an output folder that does not exist (or is not the expected client location when the consumer names a
   marker path), a proto file that does not exist, or a proto that fails to compile, **When** the step runs, **Then** it
   fails with a message naming the input and the fix, and it creates no folder tree in the wrong place.
6. **Given** generated files committed in the client repo, **When** the developer cleans or rebuilds the generation
   project, **Then** no committed generated file is deleted, and Unity `.meta` files next to generated files are never
   created, changed or deleted by the step.
7. **Given** a CI job of the game, **When** it runs the step in verify mode, **Then** the step exits non-zero, listing
   each output file that differs from what would be generated, and writes nothing.

### User Story 3 - Unity code uses generated routes and section parsers, not copied strings (Priority: P2) — FG-026 (2), FG-028

The Unity SDK and every client call routes and read sections through generated code built from the server's catalog:
route constants (and helpers for routes with parameters), section id constants and a table from section id to message
parser. A typed section accessor reads a section without the caller choosing a parser. The SDK's own framework routes
come from the same generation, so SDK and server cannot drift.

**Why this priority**: This is the client half of FG-026 and the whole of FG-028. It depends on the catalog (story 1)
and the generation step (story 2). Parsing a section with the wrong parser usually does not throw, it yields wrong data.

**Independent Test**:
- Regenerate the SDK's generated files from the framework catalog and check that they are identical to the committed
  ones (verify mode in the framework test suite).
- Check that every player-facing framework route in the catalog has a generated constant equal to the route the SDK
  sends.
- Check that the SDK runtime sources contain no hand-written route literal.
- Generate the sample game's and the consumer fixture's route and section files. Check that the sample Unity client
  compiles against them and that its hand-copied route class is gone.
- In SDK tests, read `wallet`, `inventory` and `profile` and a game section through the typed accessor after a snapshot
  and after a `SectionUpdate`.
- Check that a section id unknown to the table is kept raw and reported as unknown, not parsed.

**Acceptance Scenarios**:

1. **Given** the catalog of a host composition, **When** route code is generated for Unity, **Then** every route of the
   player API and host-endpoint surfaces with profile Player, Public or Dev gets a constant, in the form the SDK sends
   (relative to the base URL, no leading slash). No GM API surface route is generated, including Public GM routes such
   as GM login. Constant names derive deterministically from the declared route names.
   Two routes that would produce the same constant name fail generation, naming both.
2. **Given** a route with parameters (for example `GET /api/v1/player/receipts/{receiptId}`), **When** route code is
   generated, **Then** the client gets a helper that takes each parameter and returns the route with escaped values.
   Constraints, optional or catch-all parameters the helper cannot express fail generation, naming the route. A template
   with unexpanded braces is never emitted as a sendable constant.
3. **Given** the SDK of this slice, **When** it calls login, provider login, link, logout, delete account, snapshot,
   config and time, **Then** it uses the generated framework route constants. `GameServerClient.LoginRoute`,
   `ProviderLoginRoute`, `LinkRoute`, `LogoutRoute`, `DeleteAccountRoute`, `SnapshotRoute`, `ConfigRoute` and `TimeRoute`
   keep their names and values for existing callers.
4. **Given** a client-visible aggregate, **When** its wire mapper is registered, **Then** the registration names the wire
   message type, so the catalog records section id ↔ message full name for every client-visible aggregate of the host.
5. **Given** the section entries of a composition, **When** section code is generated for Unity, **Then** the client
   gets one constant per section id and a table from section id to the parser of the generated C# type of that message.
   Generation fails when a section's message is not among the protos given to the step (game sections) or shipped in the
   Unity package (framework sections), naming the section and the message.
6. **Given** a client with generated section code, **When** it reads a section through the typed accessor, **Then** it
   gets the message parsed with the parser of the table (null when the client does not have the section), and it cannot
   pass a different parser for that id. The existing `SectionStore.Get<T>(id, parser)` keeps working unchanged.
7. **Given** a snapshot or `SectionUpdate` carrying a section id the client's table does not know (server deployed with a
   new aggregate before the client update), **When** the SDK stores it, **Then** it is kept raw as today, and the typed
   path reports it as unknown instead of parsing it.

### User Story 4 - A wire mapper that drops a field fails a test, and hidden fields are declared in code (Priority: P3) — FG-027

A game developer adds a member to an aggregate state record. If the proto message or the mapper is not updated, a test from
the consumer test kit fails, naming the member or the proto field. Members kept on the server on purpose are declared next
to the mapper registration, not in a comment, and the declaration can be listed in the PCR.

**Why this priority**: The client silently loses data, and every aggregate and field added from P2 onwards is exposed.
There is no build, test or startup check today. The consumer test kit from 013 is the agreed place.

**Independent Test**:
- Run the conformance helper over every wire mapper of the framework, sample and template modules, and check that all
  pass.
- Seed the following defects one at a time and check that each is reported by name:
  - a state member not mapped;
  - a proto field never set;
  - a nested record member not mapped;
  - a hidden declaration naming a member that does not exist;
  - a hidden member that actually reaches the wire;
  - a collection member left empty by the mapper.
- Run the same helper from the consumer fixture with a game-shaped aggregate that has a nested record, a map, a list, a
  nullable member, a `DateTimeOffset` mapped to UTC milliseconds and a hidden member.

**Acceptance Scenarios**:

1. **Given** a client-visible aggregate with its wire mapper, **When** a test runs the conformance helper with a state in
   which every member (recursively, including nested records, collection elements and map values) holds a non-default
   value, **Then** the helper maps it, parses the payload back with the section's message parser, and reports every proto
   field (recursively) still at its protobuf default.
2. **Given** the same aggregate, **When** the helper changes one state member at a time, **Then** it reports every member
   whose change does not change the wire payload, unless that member is declared hidden.
3. **Given** a member declared hidden at mapper registration, **When** the helper runs, **Then** it reports the hidden
   member if changing it does change the payload (stale declaration). It does not report a proto field the declaration
   marks as allowed to stay default.
4. **Given** a hidden-member declaration naming a member path that does not exist on the state type, **When** the host
   starts, **Then** startup fails, naming the aggregate and the path.
5. **Given** a state type the helper cannot fill automatically (a member type it does not support), **When** the helper
   runs, **Then** it names each member it could not fill and fails unless the test supplies a sample value for it. It
   never skips a member silently. The test may always supply the whole sample state itself.
6. **Given** a host composition, **When** a consumer test asks the kit to check every registered client-visible aggregate
   at once, **Then** one call reports all mappers, so a new aggregate is covered without a new test.
7. **Given** the catalog export, **When** it is read, **Then** it lists each section's hidden members, so the PCR's
   "hidden fields" list can be taken from code.

### User Story 5 - The framework's own SDK, sample client and docs use the same path (Priority: P4) — FG-021, FG-026, FG-028

The framework uses its own consumer generation step for the Unity package and the sample client, and its guides describe
the declaration, generation and conformance steps for in-repo and consumer-repo modules. A reader of the consumer guide or
the "add a command" page follows one documented path.

**Why this priority**: Using the path itself is what keeps it working after this slice (every framework build exercises
it). The docs must describe shipped behaviour, so this comes last.

**Independent Test**:
- Build `sdk/GameServer.Client` and the sample client generation through the consumer step. Check that the generated
  output in the Unity package and in `samples/SampleGame/KestrelDemo` is unchanged apart from the intended additions.
- Check that existing `.meta` GUIDs of generated files are unchanged.
- A reviewer follows the consumer guide and the updated §4.10 / §5 of `02-them-command.html` to add one game command
  with its route declaration, regenerate Unity code and call it from a fixture client, and records every missing or
  wrong step.

**Acceptance Scenarios**:

1. **Given** the framework repo, **When** the SDK's generated code is rebuilt, **Then** it is produced by the same consumer
   generation step (framework protos, framework routes, framework sections). Existing file paths under
   `Runtime/Generated` and their committed `.meta` files stay as they are, and each new generated file in the package
   ships with a committed `.meta`.
2. **Given** the sample game, **When** its Unity code is regenerated, **Then** `sample_game.proto`, the sample routes and
   the sample sections are generated into `KestrelDemo` by the consumer step (no longer by the SDK csproj), and
   `SampleGameClient.cs` uses the generated constants and typed sections instead of `SampleGameRoutes` and string ids.
3. **Given** `docs/guides/consumer-guide.md` §10, `docs/html/02-them-command.html` §4.10, §5 step 8 and the checklist, and

   typed mapper registration with hidden members, the conformance test, the generation step (in-repo and consumer-repo
   variants), and calling the generated constant from Unity. No page tells a consumer to edit a framework file.

### Edge Cases

- **Health probes** (`/health/live` is mapped with `MapHealthChecks`, so it has no method metadata): the catalog must be
  able to declare "any method" for such endpoints. They are unversioned (OBS-03) and stay valid catalog entries. They
  are Public host endpoints, so they get generated constants like `/v1/time` (FR-032). That is harmless, and it is
  useful for a client reachability check.
- **Conditional framework routes**: GM OpenAPI is mapped only when development tools are allowed and the GM API is mapped.
  Its absence elsewhere is not a missing route.
- **Host-only endpoints** mapped in a game's `Program` (a webhook, a custom probe): they must be declared through a host
  declaration. Undeclared, the host does not start.
- **Same route, two methods** (one declaration per method, or one declaration listing both): both forms must match the
  mapped metadata. One mapped method undeclared is a fault.
- **Route templates differing only in case or leading slash**: ASP.NET routing matches case-insensitively, so a case
  difference is not a 404. The check still requires the mapped template to equal the declaration after leading-slash
  normalization, so the catalog stays the single canonical text.
- **Parameter names**: `{playerId}` vs `{id}` in the template is a mismatch (the template differs). Route constraints in a
  template are compared as text.
- **Endpoints from libraries or `EndpointDataSource`s added by the host**: they are enumerated like any other. A
  non-route endpoint type is ignored, as in the existing validators.
- **Endpoints added to the data source after the first request**: out of contract. The framework checks the endpoint set
  once, before serving. Dynamic endpoint sources are not supported and are documented as such.
- **Request-time Dev refusal of slice 013** (FR-003 of 013): stays as defense in depth for any endpoint the pre-serving
  check cannot see.
- **`--provision` mode**: maps no traffic. The catalog declarations (duplicate names, invalid templates, stale hidden
  members) are still validated, but the mapped-vs-declared comparison is not, because nothing is mapped.
- **A module declares a route but the host maps the module's surface with a different module instance or replaced
  handler** (EXT-01..05, policy replacement): the declaration belongs to the module name. A replaced handler for the same
  operation and route is not a fault.
- **Two modules declaring the same route** (method + template): startup fails (as duplicate route+method today).
- **Generated constant name collisions across framework and game** (a game route named like a framework route): game
  output contains only game entries (framework entries ship in the Unity package). A game declaration that duplicates a
  framework name or route fails at startup (FR-007).
- **Game proto declaring the same package/message as a framework proto**: protoc or Unity compile error. Generation
  reports duplicate full names before writing.
- **Proto `csharp_namespace` absent**: the namespace comes from the proto package, as protoc does. The step does not
  invent one.
- **Output folder layout**: protoc output depends on the proto root. The step produces a documented, stable layout (flat
  by default, as the first consumer chose; the framework keeps its existing nested layout for `core.proto`), so moving the
  checkout does not move files.
- **Mixed `/` and `\` in paths** (FG-021 trap: Grpc.Tools then does not recognise its own output and only warns): the step
  normalizes paths, and a missing expected output is an error, not an MSBuild warning that `TreatWarningsAsErrors` does not
  catch.
- **Windows and Linux line endings**: the framework repo stores LF (`.gitattributes eol=lf`). The SDK output is generated
  in LF, and a consumer may choose CRLF. Rerunning on a working tree whose git normalizes endings shows no change in
  `git status`.
- **Unity immutable package folder**: a new generated file in `com.gameserver.client` without a committed `.meta` is
  ignored by Unity when the package comes from a git URL. Every generated file in the package has one (FR-034).
- **IL2CPP stripping**: the generated parser table references the generated types statically, so it needs no reflection
  and no extra `link.xml` entry. The game's existing `link.xml` may stay.
- **A typed mapper whose function returns a subtype or a different message at run time**: impossible with a typed
  registration. An untyped registration (kept, deprecated) appears in the catalog without a message name, gets an id
  constant but no parser entry, and logs one startup Warning naming the aggregate.
- **Two mappers registered for one aggregate id** (today the last silently wins): startup fails, naming the aggregate
  (FR-054).
- **Section of a non-client-visible aggregate**: not in the section table, and never in a snapshot.
- **Conformance on `oneof`, `optional` proto3 fields, enums whose zero value is meaningful, maps with default-valued
  entries, and repeated scalar fields**: "non-default" for a repeated or map field means non-empty with non-default
  elements. A proto field whose meaningful value is the default (an enum zero) can be declared "may stay default".
- **State members that are computed properties** (no setter, not serialized): they are not state members for the helper.
  The helper considers the members the aggregate serializer persists.
- **A `DateTimeOffset` mapped to milliseconds loses sub-millisecond precision**: the perturbation used by the helper
  changes values by at least one wire unit (documented), so precision loss is not reported as a dropped member.
- **SDK base URL with a path prefix** (`https://host/game1/`): generated constants are relative, so the base path is
  kept. A constant with a leading slash would drop the prefix (`new Uri(baseUrl, route)`), which is why generated client
  routes never start with `/`.
- **Older Unity clients after a server adds a route or section**: they keep working (unknown sections kept raw). A
  renamed route is a breaking change of the player API (ARC-08) whatever the catalog says.

## Requirements *(mandatory)*

### Functional Requirements

**Route catalog (FG-026 (1); ARC-03, ARC-07, API-02, SEC-08, SEC-09, constitution II)**

- **FR-001** (FG-026): The framework MUST expose one public, read-only route catalog of a host. Each entry holds:
  - a stable route name;
  - the HTTP method(s), or "any";
  - the route template;
  - the security profile;
  - the owning module (or "platform" / "host");
  - the surface (player API, GM API, host endpoints);
  - the command operation, when any;
  - an optional hosting condition.

  The catalog is available after the host is built and also without starting a server (for codegen and tests).
- **FR-002** (FG-026): Every route the framework can map MUST be declared in the catalog and readable from consumer code
  through public API. This covers:
  - the platform routes: time, snapshot, receipt lookup, config;
  - the observability health probes;
  - the GM OpenAPI document (conditional);
  - identity (guest/provider login, logout, display name, link, delete account, GM ban/unban/cancel deletion);
  - IAP purchase;
  - economy GM adjust and ledger;
  - cheat grant;
  - every GM module route (auth, CSRF, SSO start/callback, me, UI, health, players, receipts, audit, staff, gate,
    maintenance, minimum client version, key rotation, version).

  No consumer needs to copy a framework route string. `CoreEndpoints` route constants stop being the only, internal source.
- **FR-003** (FG-026): A game module MUST declare its routes through the same mechanism the framework modules use, as part
  of its module registration. A host MUST be able to declare routes it maps itself outside any module.
- **FR-004** (FG-026, ARC-01, ARC-02): Route declarations MUST be expressible in a module's business project without HTTP,
  ASP.NET Core or Protobuf dependencies (the architecture rule for business projects stays green). Typed wire information

### Key Entities

- **Route catalog**: the set of route declarations of a host: name, method(s), template, profile, owner, surface,
  operation, condition. It is built from module and host declarations.
- **Route declaration**: one entry, written once in the module (or host) and used by mapping code, the endpoint check and
  codegen.
- **Section entry**: client-visible aggregate id ↔ wire message full name ↔ owning module, plus hidden members and
  allowed-default fields.
- **Endpoint check**: the pre-serving comparison of mapped endpoints with the catalog, plus the existing endpoint
  validations over the final endpoint set.
- **Consumer generation step**: a framework-provided, deterministic generator of message C#, route code and section code
  for Unity, with a verify mode.
- **Generated route code / section code**: client-side constants, parameter helpers, section ids and the id → parser
  table.
- **Typed section accessor**: SDK read path that pairs a section id with its generated parser.
- **Conformance check**: a consumer test kit helper that proves a mapper carries every non-hidden state member and sets
  every proto field.

## Assumptions

- Direction B (owner, 2026-11-03) is binding: the catalog is the server-side source, declared in module and host
  registration. The check compares the mapped endpoints with it. Direction A (per-repo constants) and C (proto route
  option) are not used.
- The check runs in every environment, like the other startup validations, and has no opt-out. Endpoints must be declared
  to exist. Without that, the check cannot catch the runtime-only mismatch FG-026 is about.
- Late-mapped endpoints (after `UseGameServer`) can be validated before Kestrel accepts the first request. The plan
  confirms the hosting hook. If no hook sees the final endpoint set before listening, the plan reports it and the fallback
  is a refusal at the first request with the same report, never silent acceptance.
- GM routes are in the catalog (server-side check, docs) but are not generated for Unity. The GM frontend belongs to
  another developer and uses the OpenAPI document (owner, 2026-10-27). No TypeScript generation.
- Dev (cheat) routes are generated for Unity like other player-facing routes. The server refuses them outside
  Development/Test (013). Shipping a route string in a release client discloses nothing the server accepts.
- Generated client routes are relative to the SDK base URL (no leading slash), matching what the SDK sends today
  (`new Uri(BaseUrl, route)`).
- The generation step runs with the .NET SDK outside the Unity Editor. No Unity menu item or Editor codegen.
- The first consumer generates from the server repo into a sibling client checkout, as today. A catalog export (FR-030)
  that lets the client repo generate on its own is optional in this slice.
- The section ↔ message contract is not added to the `Section`/`SectionUpdate` wire messages (bytes per section per
  response; API-03 field stability). It lives in the catalog, PCR and generated code.
- The untyped mapper registration stays (obsolete) through `v0.7.x`. Removal is a later breaking change announced in
  release notes.
- The conformance check considers the members the aggregate document serializer persists. Computed members are not state.
- The framework keeps the existing nested output layout for `core.proto` and the flat layout for module protos in the
  Unity package, to keep `.meta` GUIDs stable. Consumers get a flat layout by default.
- `Google.Protobuf` 3.36.2 (CPM and Unity dll) and `Grpc.Tools` 2.84.0 stay the pinned pair in this slice. Bumping them is
